# Authorization and Store Onboarding Design

## Intent

Build the backend authorization and onboarding foundation for the shoe-store inventory application. New users verify ownership of their email before an account exists, then either create one store or join one store. Authentication, recovery, membership, and role enforcement must be safe to deploy through the existing Docker stack and must not add frontend code.

## Scope

This phase covers:

- Registration with first name, last name, email, phone number, password, password confirmation, and email OTP verification.
- Phone-number/password login, seven-day sessions, sign-out, and server-side session invalidation.
- Email-based password reset with OTP verification and forced sign-in on every device afterward.
- Provider-neutral SMTP delivery prepared for a future `noreply@<owned-domain>` sender.
- Post-registration onboarding: create a store or join an existing store.
- Unique store entry codes, join requests, phone-number invitations, acceptance, membership listing, role changes, and access removal.
- Owner, manager, and seller authorization rules needed by the existing endpoints.
- OpenAPI, environment examples, Docker configuration, migration, tests, and durable progress documentation.

Inventory behavior, sales presentation, and frontend implementation are separate later phases. Existing inventory and sales endpoints will only be changed where required to enforce the agreed roles.

## Confirmed Business Rules

### Registration and sessions

- Registration fields are first name, last name, email, phone number, password, and password confirmation.
- Email and phone number are unique, normalized identifiers.
- No user or store is created before email verification succeeds.
- Verification and reset codes are six digits, expire after 10 minutes, can be resent after 60 seconds, and allow at most five failed attempts.
- Code requests and verification attempts are rate-limited by identifier and IP address.
- Codes are stored as keyed digests, never plaintext.
- Login continues to use phone number and password.
- Sessions last seven days.
- Completing a password reset increments the account session version, invalidating every existing session, and does not automatically log the user in.
- Reset-start responses do not reveal whether an email exists.

### Email delivery

- Application code uses a small mailer interface and an SMTP implementation rather than a provider-specific API.
- SMTP settings and the full `EMAIL_FROM` address are environment configuration. The display name defaults to `noreply`.
- Until a real owned domain and credentials are configured, local/test environments use an injected recording mailer. A disabled production mailer returns a safe service-unavailable response; it never reports that mail was sent when it was not.
- A free SMTP provider such as Brevo can later be configured without changing endpoint logic. DNS authentication remains an operational step.

### Store onboarding and membership

- Every account may have at most one active store membership, regardless of role.
- After verification, a user chooses either to create a store or to join one.
- Creating a store makes that user its permanent owner. An account that already has a membership cannot create or join another store.
- Each store has a random unique entry code. A user supplies the code to create a pending join request. The code can be regenerated by the owner, invalidating the old code.
- The approver chooses `manager` or `seller` when approving a join request.
- Invitations target an existing account by exact normalized phone number. Unknown phone numbers return user-not-found and create nothing.
- An invitation grants no access until the invited user accepts it.
- Pending requests and invitations do not count as membership. Accept/approve operations recheck that the target user is still unaffiliated.
- Conflicting pending invitations/requests are closed when a membership is created.

### Role hierarchy

| Capability | Owner | Manager | Seller |
|---|---:|---:|---:|
| View store and inventory | Yes | Yes | Yes |
| View landing/initial price | Yes | Yes | No |
| Add/edit/delete products or stock | Yes | Yes | No |
| Sell products | Yes | Yes | Yes |
| View all store sales | Yes | Yes | No; own sales only |
| Edit store profile/social links | Yes | No | No |
| Invite/approve/remove sellers | Yes | Yes | No |
| Create/promote/demote/remove managers | Yes | No | No |
| Regenerate entry code | Yes | No | No |
| Remove/demote owner | Never | Never | Never |

The database's global `users.role` is not the source of store permissions. Store permissions come from the authenticated user's single `store_users.role` membership.

## API Design

All responses use the existing JSON error/envelope conventions. Public initiation endpoints are rate-limited and return generic messages where account enumeration is a risk.

### Authentication

- `POST /api/auth/signup/start` validates the six registration fields, rejects an existing phone/email, creates or replaces a pending signup challenge, and sends a code.
- `POST /api/auth/signup/verify` consumes `{ challengeId, code }`, creates the user transactionally, starts a session, and returns `{ user, store: null, onboardingRequired: true }`.
- `POST /api/auth/verification/resend` resends an eligible unconsumed challenge without extending attempts indefinitely.
- `POST /api/auth/login` retains phone/password login and returns the current membership/store.
- `GET /api/auth/me` returns user, store, onboarding state, and effective permissions.
- `POST /api/auth/signout` clears the current cookie.
- `POST /api/auth/signout-all` increments session version and clears the current cookie.
- `POST /api/auth/password-reset/start` accepts an email and always returns the same accepted response.
- `POST /api/auth/password-reset/verify` consumes the email code and returns a short-lived, one-use opaque reset token.
- `POST /api/auth/password-reset/complete` accepts the reset token, password, and password confirmation; updates the bcrypt hash, consumes the token, increments session version, and clears the cookie.
- `POST /api/auth/email/start` and `POST /api/auth/email/verify` let migrated accounts without email attach and verify a unique email while authenticated.

The legacy one-call `POST /api/auth/signup` is removed from the public contract because it bypasses verification. During deployment it returns an explicit migration error rather than creating unverified accounts.

### Store onboarding and access

- `POST /api/store` creates the caller's store and owner membership transactionally.
- `GET /api/store` is available to any store member; sensitive membership data remains in dedicated endpoints.
- `PUT /api/store` is owner-only and supports name, optional description/photo, Telegram fields, and Instagram fields.
- `POST /api/store/entry-code/regenerate` is owner-only and returns the new code once.
- `POST /api/store/join-requests` accepts an entry code for an unaffiliated user.
- `GET /api/store/join-requests` lists pending requests for owner/manager.
- `POST /api/store/join-requests/:id/approve` accepts a role. Managers may approve only `seller`; owners may approve either role.
- `POST /api/store/join-requests/:id/reject` rejects a request with the same hierarchy.
- `POST /api/store/invitations` accepts phone number and role. Managers may invite only sellers; owners may invite managers or sellers.
- `GET /api/auth/store-invitations` lists the caller's pending invitations.
- `POST /api/auth/store-invitations/:id/accept` creates membership after rechecking exclusivity.
- `POST /api/auth/store-invitations/:id/reject` closes the invitation.
- `GET /api/store/members` is available to owner/manager.
- `PATCH /api/store/members/:userId` changes a manager/seller role and is owner-only.
- `DELETE /api/store/members/:userId` lets an owner remove managers/sellers and a manager remove sellers only.

## Persistence and Security

A versioned migration will:

- Add nullable unique `users.email`, `email_verified_at`, and `session_version` fields so existing accounts remain usable.
- Add store description/social fields missing from the runtime contract, a unique entry-code digest, and explicit owner linkage.
- Add signup/reset challenges and one-use reset tokens with expiry, attempt, resend, consumption, and audit timestamps.
- Add store invitations and evolve join requests for resolution/audit data.
- Enforce one membership per user with a unique key after detecting conflicting legacy data. The migration fails with a reconciliation error instead of silently discarding memberships.

OTP and entry codes are compared through keyed HMAC digests using a dedicated secret. Passwords remain bcrypt hashes. Transactions and row locks protect every create/approve/accept/reset operation from double submission. Expired data is ignored by reads and can be deleted by a bounded cleanup operation.

Rate limiting uses a database-backed window so it works across Docker replicas and process restarts. Limits are applied to request IP plus normalized email/phone; responses never expose code values or password material. Logs contain event identifiers, not secrets or full reset tokens.

## Approaches Considered

### Chosen: database challenges, versioned cookie sessions, SMTP adapter

This fits the existing Express/MySQL service, survives restarts, supports multiple server replicas, preserves the current cookie-based clients, and allows any SMTP provider later. It adds schema and transactional complexity but gives deterministic revocation and auditability.

### Rejected: in-memory OTPs and rate limits

This is quicker but loses challenges on restart, behaves incorrectly with multiple containers, and cannot safely enforce abuse limits. It is unsuitable for a deployable server.

### Rejected: external identity/email platform

Services such as Auth0, Firebase, or provider-specific passwordless authentication could reduce custom security code, but they would replace the existing phone/password model, introduce vendor coupling, and require product/account decisions not currently desired.

## Compatibility and Deployment

- Existing users keep phone/password login. Accounts without email are prompted to verify one before email recovery is available.
- Existing sessions without a session version become invalid after deployment; users sign in again once.
- Schema migration runs explicitly through the existing migrator before the backend is recreated.
- Docker Compose passes email/OTP configuration but does not embed credentials.
- OpenAPI and the integration guide become the canonical frontend contract.
- No frontend files are created or modified.

## Success Criteria

- Unit and MySQL integration tests prove verification-before-creation, reset revocation, one-store membership, invite acceptance, approval hierarchy, seller restrictions, transaction races, rate limits, and non-enumerating responses.
- Every new route appears in OpenAPI and every removed route is absent or explicitly deprecated.
- `npm test` and `npm run test:integration` pass.
- Migration status/apply/status succeeds against the disposable MySQL test service.
- Docker image build and Compose configuration validation succeed.
- The repository progress document identifies completed work and the next business-logic phase.
